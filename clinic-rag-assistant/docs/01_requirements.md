# 01. 要件定義

## 1. 背景と課題(想定)

架空の美容クリニック「Lumière Clinic」は都内3院を展開し、看護師・カウンセラー・受付スタッフ約40名が在籍する。
以下の業務課題を抱えている想定。

- 施術メニューが50種以上あり、料金・禁忌・術後ケアの詳細を全スタッフが暗記できない
- マニュアルはPDF/Wordで共有フォルダに散在し、検索性が低い
- 新人スタッフの質問がベテランに集中し、教育コストが高い
- 誤案内(料金・ダウンタイム・禁忌の誤り)は患者トラブルに直結するため、**根拠のない回答は許されない**

## 2. ソリューション概要

社内文書を対象としたRAG検索システムを提供する。
スタッフが自然文で質問すると、関連文書を検索し、**引用元を明示した回答**を返す。

## 3. 想定ユーザーとユースケース

| ユーザー | ユースケース例 |
|---|---|
| 受付スタッフ | 「医療脱毛の当日キャンセルのキャンセル料は?」 |
| カウンセラー | 「ダーマペンとポテンツァの違いを患者に説明したい」 |
| 看護師 | 「ボトックス施術後に飲酒はいつから可能?」 |
| 新人スタッフ | 「初診の患者様への案内フローを教えて」 |
| 管理者 | 文書の追加・更新・削除、利用状況の確認 |

## 4. 機能要件

### 4.1 検索・回答(スタッフ向け)
- FR-01: 自然文による質問入力
- FR-02: 関連文書チャンクのベクトル検索(上位k件)
- FR-03: 検索結果を根拠としたClaude APIによる回答生成
- FR-04: 回答には必ず引用元(文書名・セクション)を付与する
- FR-05: 根拠が見つからない場合は「該当する社内文書が見つかりません」と回答し、推測で答えない
- FR-06: 会話履歴を踏まえたフォローアップ質問(同一セッション内)

### 4.2 文書管理(管理者向け)
- FR-07: 文書のアップロード(Markdown/テキスト)と自動チャンク分割・embedding生成
- FR-08: 文書の更新(旧チャンクの無効化と再取り込み)
- FR-09: 文書の削除(論理削除、検索対象から即時除外)
- FR-10: 取り込みステータスの確認(処理中/完了/失敗)

### 4.3 評価(開発者向け)
- FR-11: ゴールデンデータセットに対する回帰テストの実行
- FR-12: 検索精度(Recall@k)・回答品質スコアのレポート出力
- FR-13: CI(GitHub Actions)での自動実行

## 5. 非機能要件

| 項目 | 目標値 | 根拠 |
|---|---|---|
| 検索APIレイテンシ | p95 < 3,000ms(LLM生成含む) / 検索のみ p95 < 200ms | 接客中の利用を想定。LLM生成はストリーミングで体感を改善 |
| 同時接続 | 40名同時利用に耐える(ピーク 20rps 想定) | 全スタッフが朝礼後に一斉利用するケース |
| 可用性 | 業務時間内(10:00-20:00)の稼働を優先 | 社内ツールのためSLAは緩め。ただしキャッシュでDB/API障害時の劣化運転を考慮 |
| コスト | Claude API呼び出しをキャッシュで削減(同一質問の再生成を回避) | 社内FAQは同種の質問が繰り返される性質を利用 |
| セキュリティ | 社内認証(メール+パスワード、将来的にSSO)。文書は院外秘 | 患者個人情報は扱わない(文書はマニュアル類のみ)スコープとする |

## 6. スコープ外

- 患者向けの公開チャットボット(誤案内リスクが高いため本フェーズでは対象外)
- 患者個人情報・カルテ情報の検索(法規制対応が必要なため対象外)
- PDF/Word/画像のパース(Phase 1はMarkdown/テキストのみ。拡張ポイントとして設計)

## 7. ダミーデータ(コーパス)

架空クリニックの社内文書 約30本をシードデータとして用意する。

- 施術マニュアル: 医療脱毛 / ダーマペン / ポテンツァ / ボトックス / ヒアルロン酸 / ピーリング 等 12本
- 予約・キャンセルポリシー: 3本
- 術後ケアFAQ: 8本
- 接客・案内マニュアル: 5本
- 就業・院内ルール: 2本

※ すべて架空の内容であり、実在の医療情報としての正確性は担保しない(ポートフォリオ用ダミー)。文書内にその旨を明記する。
