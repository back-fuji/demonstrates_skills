# 06. 負荷試験計画とチューニング方針

## 1. 目的

「壊れる・遅いことを計測で証明してから、直し、改善を数字で示す」プロセスを記録する。
最終成果物はbefore/after比較表とグラフ(READMEに掲載)。

## 2. 計測環境

- ローカルDocker Compose(スペックをREADMEに明記し、絶対値より**相対改善**を主眼とする)
- ダミーデータ: 文書30本 → チャンク約600件(Phase 3ではベンチ用に合成データで1万チャンクまで増幅)
- LLM/embedding呼び出しは**モック可能にする**(負荷試験時は固定レイテンシのフェイクに差し替え。外部APIに負荷をかけない+コストゼロ+計測の再現性)
  - ただし「実API込みのレイテンシ内訳」も別途1回計測し、ボトルネックの所在(自前処理 vs 外部API)を示す

## 3. k6シナリオ

### S1: 通常負荷(ベースライン)
- 40 VU(仮想ユーザー)が思考時間3〜10秒で検索を実行、5分間
- 質問は30種のプールからランダム(キャッシュヒット率が現実的になるよう分布を設定: 上位5質問で50%)

### S2: スパイク(朝礼後の一斉利用)
- 10秒間で0→100VUへ急増、1分維持
- 観察点: キャッシュ期限切れと重なったときのDB/API殺到(スタンピード)

### S3: キャッシュスタンピード再現
- 人気質問1件のキャッシュをテスト用エンドポイントで強制失効させた直後に100VUが同一質問
- 対策前: フェイクLLMへの同時リクエスト数がVU数分発生することを確認
- 対策後(SWR+ロック): 生成処理が1件に収束することを確認

### S4: 取り込み競合
- 同一文書への更新リクエストを10並列で送信
- 対策前: 二重取り込み・チャンク重複の発生件数を記録
- 対策後(楽観ロック): 1件成功・9件が409で、データ不整合ゼロを確認

## 4. 計測指標

| 指標 | 説明 |
|---|---|
| rps | スループット |
| p50 / p95 / p99 レイテンシ | 検索API(LLM除く検索部分と、全体の両方) |
| エラー率 | 5xx / タイムアウト |
| LLM(フェイク)呼び出し回数 | キャッシュ効果・スタンピード対策の直接指標 |
| DBクエリ時間 | pgvector検索の内訳(Laravel Telescope / pg_stat_statements) |

## 5. 改善ステップ(仮説)

各ステップで S1/S2 を再計測し、表に追記していく。

| Step | 施策 | 期待効果 |
|---|---|---|
| 0 | ベースライン(キャッシュなし・逐次embedding) | — |
| 1 | 回答キャッシュ(単純TTL) | 人気質問のp95大幅改善。ただし期限切れ時にスパイク脆弱 |
| 2 | stale-while-revalidate + 再生成ロック | スタンピード解消。LLM呼び出し回数がVU数に依存しなくなる |
| 3 | pgvectorインデックス比較(HNSW vs IVFFlat vs インデックスなし) | 1万チャンクでの検索p95とRecallのトレードオフ表(ADR-003の実証) |
| 4 | 取り込みの楽観ロック | S4の不整合ゼロ化 |

## 7. 面談で語るポイント

- 平均ではなくp95/p99で語る理由(テールレイテンシがUXを決める)
- 「対策前に壊れる状態を再現した」こと自体が価値(S3/S4)
- 外部API依存システムの負荷試験ではモック差し替えが必須という実務知見
