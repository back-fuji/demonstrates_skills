# 05. 評価ハーネス設計

## 1. なぜ評価ハーネスが必要か

LLMを使った機能は「動いた」と「正しく動き続ける」の間に大きな溝がある。

- プロンプトを1行変えただけで、別の質問への回答が壊れる(サイレントデグレ)
- モデルのバージョン更新で挙動が変わる
- 文書を追加したら、既存質問の検索結果が変わる

通常のユニットテストは「出力が固定」の前提だが、LLM出力は非決定的。
そこで **ゴールデンデータセットに対する自動採点(回帰テスト)** を仕組み化し、変更のたびに品質を数値で確認できるようにする。

## 2. 評価の2層構造

RAGの失敗は「検索が外れた」か「生成が外れた」のどちらかであり、切り分けて計測する。

### 層1: 検索精度(Retrieval)— 決定的・高速・安価

- 指標: **Recall@k** — 正解チャンク(`expected_chunk_ids`)が検索上位k件に含まれた割合
- LLM呼び出し不要なので、チャンク戦略やインデックス変更のたびに気軽に回せる
- 目標値: Recall@8 ≥ 0.9

### 層2: 回答品質(Generation)— LLM-as-a-Judge

- 生成された回答を、別のClaude呼び出し(Judge)が採点する
- Judgeへの入力: 質問 / 生成回答 / 期待要点(`expected_answer_points`)/ 引用チャンク
- 採点基準(1〜5点、観点別):
  - **忠実性(Faithfulness)**: 引用チャンクにない情報を捏造していないか
  - **網羅性(Coverage)**: 期待要点をどれだけ含むか
  - **引用の正しさ**: 引用元の提示が適切か
- Judge出力はJSON強制(`{"score": 4, "missing_points": [...], "hallucinations": [...], "reason": "..."}`)
- 目標値: 平均 ≥ 4.0、忠実性で3点未満のケースは0件

### 特殊カテゴリ: no_answer ケース

「社内文書に存在しない質問」(例: 「他院の料金は?」)に対して、**推測せず『見つかりません』と答えられるか**をテストする。
医療・美容ドメインでは誤答が実害になるため、これを独立カテゴリとして必ず含める。
判定: 回答に定型の断り文言が含まれ、かつ捏造情報がないこと。

## 3. ゴールデンデータセット

- 初期30ケースを手作りでシード(fact 12 / policy 8 / comparison 5 / no_answer 5)
- 運用中の👎フィードバックから新規ケースを追加していく想定(feedback API → eval_cases化)
- ケースはDBとYAMLの両方で管理(YAMLがマスタ、`eval:seed`でDBへ投入。Gitで差分レビュー可能にするため)

```yaml
# database/eval/cases/policy_001.yaml
question: "医療脱毛を当日キャンセルした場合のキャンセル料は?"
category: policy
expected_chunk_keys:            # chunk_idは環境依存のため、document+sectionで指定
  - "予約・キャンセルポリシー#当日キャンセル"
expected_answer_points:
  - "施術料金の50%が発生する"
  - "無断キャンセルは100%"
  - "体調不良の場合は前日までの連絡で免除"
```

## 4. 実行フローとCI

```
php artisan eval:run
  ├── 1. 全eval_casesをロード
  ├── 2. 各ケースで検索実行 → Recall@k判定(層1)
  ├── 3. 回答生成 → Judge採点(層2)※ --only=retrieval でスキップ可
  ├── 4. eval_runs/eval_resultsへ保存
  └── 5. Markdownレポート出力(前回runとの差分表示)
```

レポート例:
```
## Eval Report (run #12, git: a1b2c3d, prompt: v3)
| 指標 | 今回 | 前回 | 差分 |
|---|---|---|---|
| Recall@8        | 0.93 | 0.90 | +0.03 ✅ |
| Judge平均        | 4.2  | 4.3  | -0.1 ⚠️ |
| 忠実性<3のケース | 0    | 0    | - |
| no_answer正答率  | 5/5  | 4/5  | +1 ✅ |

### デグレしたケース
- policy_003: Judge 5→3。missing: "無断キャンセルは100%"
```

CI(GitHub Actions):
- PR時: `eval:run --only=retrieval`(無料・高速)を必須チェックに
- main merge時 / prompt変更時: フル実行(Judge含む)。コスト管理のためケース数上限とAPIコスト概算をログに出す
- しきい値割れ(Recall@8 < 0.85 or 忠実性<3が1件以上)でCIを落とす

## 5. コスト設計

- Judge採点は30ケース × (生成+採点) ≒ 60 API呼び出し/回。フル実行は1日数回まで、と運用ルール化
- 検索層のみの実行はAPIコストゼロ(embeddingはクエリ30件分のみ)→ 開発中はこちらを高頻度で回す
- 評価用のembeddingとJudge結果はキャッシュし、同一入力の再課金を避ける

## 6. 面談で語るポイント(このドキュメントの狙い)

- 「AIを組み込めます」ではなく「**AI機能の品質をCIで守れます**」を示す
- 検索と生成を分離して計測する切り分け思考
- no_answerテストという、ドメイン(医療)理解に基づく安全設計
