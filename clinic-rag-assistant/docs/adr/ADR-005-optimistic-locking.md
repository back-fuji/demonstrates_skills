# ADR-005: 文書更新の同時実行制御に楽観ロックを採用する

- Status: Accepted
- Date: 2026-07

## Context

文書の更新(PUT /api/documents/{id})は「旧チャンク無効化 → 再チャンク化 → embedding再生成」という重い処理を伴う。
複数の管理者が同一文書を同時編集した場合、後勝ちによる編集消失や、取り込みジョブの二重実行によるチャンク重複が起きうる。

同時実行制御の選択肢:

| 方式 | 仕組み | 向くケース |
|---|---|---|
| 悲観ロック(SELECT FOR UPDATE) | 読み取り時点で行ロックし他を待たせる | 衝突が頻発する(予約の人気枠など) |
| 楽観ロック(versionカラム) | 更新時にversion一致を確認、不一致なら409 | 衝突が稀 |

## Decision

楽観ロック(documentsテーブルのversionカラム + If-Matchヘッダ)を採用する。

```sql
UPDATE documents
SET content = :content, version = version + 1, status = 'processing'
WHERE id = :id AND version = :expected_version;
-- affected rows = 0 なら 409 Conflict
```

## Rationale

1. **衝突頻度**: 文書編集の競合は「たまたま2人が同じマニュアルを同時に直す」程度で稀。稀な衝突のために全更新をロック待ちさせる悲観ロックは過剰
2. **UX**: 衝突時は「他の管理者が更新しました。最新版を確認してください」と返す方が、暗黙の後勝ち(編集消失)より安全
3. **ジョブとの整合**: 取り込みジョブもversionを引数に持ち、実行時点でversionが進んでいたら自身を破棄する(古いジョブが新しい編集を上書きしない)

## Consequences

- (+) ロック待ちなし、デッドロックリスクなし、編集消失ゼロ
- (−) クライアント側で409時の再取得UIが必要
- 対比として: もし本システムに「予約枠の確保」のような高競合処理があれば悲観ロック(SELECT FOR UPDATE)を選ぶ。**方式はドメインの衝突頻度で選ぶ**というのが本ADRの要点であり、負荷試験S4で楽観ロックの正しさを実証する
