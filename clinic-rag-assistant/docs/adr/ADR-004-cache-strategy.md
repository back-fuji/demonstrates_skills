# ADR-004: 回答キャッシュにstale-while-revalidate + 再生成ロックを採用する

- Status: Accepted
- Date: 2026-07

## Context

LLM回答生成は1回2〜5秒かかり、APIコストも発生する。社内FAQは同種の質問が繰り返されるため、キャッシュ効果が大きい。
一方、単純なTTLキャッシュには**キャッシュスタンピード**の問題がある: 人気質問のキャッシュが失効した瞬間、待機していたリクエスト全てがLLM生成に殺到し、レイテンシ悪化とコスト浪費を招く。

## Decision

以下の3層戦略を採用する。

1. **キー設計**: 質問文を正規化(トリム・全半角統一・小文字化)したハッシュ。※完全一致のみ。意味的に同じ質問の同一視(セマンティックキャッシュ)はPhase 3の拡張候補
2. **stale-while-revalidate**: TTL(1時間)切れ後もstale値を24時間保持。期限切れアクセス時はstale値を即返しつつ、裏でキューにより再生成
3. **再生成ロック**: 再生成は`Cache::lock()`で排他し、同時失効時も生成処理を1件に収束させる

## Rationale

1. **UX**: 社内マニュアルの回答は数時間古くても実害がほぼない(文書更新時は該当キャッシュを明示的にパージする)。「待たせない」ことの価値が「最新である」ことを上回る
2. **コスト**: LLM呼び出し回数がアクセス数ではなく質問種類数に比例するようになる
3. **スタンピード対策の2方式比較**: 「ロックのみ(先頭1件が生成、他は待つ)」はstale値がない初回に全員が待たされる。SWR併用なら2回目以降は誰も待たない。両方の長所を組み合わせる

## Consequences

- (+) 人気質問のp95が劇的に改善(負荷試験S3で実証予定)、API費用削減
- (−) 文書更新→回答反映にラグ → 文書更新イベントでカテゴリ単位のキャッシュパージを実装
- (−) 完全一致キャッシュのためヒット率に上限 → ヒット率を計測ログに残し、セマンティックキャッシュ導入判断の材料にする
